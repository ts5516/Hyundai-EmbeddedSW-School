### 소프트웨어 테스팅: 결함 관리 및 테스트 설계 기법

이 섹션에서는 소프트웨어 품질을 확보하기 위한 테스팅의 역할, 결함 관리 프로세스, 그리고 다양한 테스트 설계 기법에 대해 다룹니다.

**1. 테스팅과 결함 관리의 기본 개념**

*   **테스팅 대 디버깅 (Testing vs. Debugging)**
    *   **테스팅**은 프로그램이 사용 가능한지 확인하기 위해 **결함이 존재함을 밝히는 활동**입니다.
    *   **디버깅**은 발견된 결함을 **수정(해결)하는 활동**입니다.
    *   결함 발견(테스팅) -> 결함 수정(디버깅) -> **재테스팅**(결함 해결 확인)의 순서로 진행됩니다.
*   **회귀 테스트 (Regression Test)**
    *   소프트웨어 변경이 기존에 올바르게 작동하던 기능에 예기치 않은 **부작용(Side Effect)을 유발하지 않았는지 확인**하는 테스트입니다.
    *   A-SPICE 4.0의 시스템 및 소프트웨어 엔지니어링 프로세스(SYS.4, SYS.5, SWE.4, SWE.5)의 기본 프랙티스(BP)에서 **회귀 검증(regression verification)**에 대한 고려가 요구됩니다.

**2. 효과적/효율적 테스팅 및 리스크 관리**

*   **효과적(Effective) 테스팅**은 계획하거나 원했던 테스트 결과를 도출하는 데 중점을 둡니다.
*   **효율적(Efficient) 테스팅**은 가용한 자원(시간, 자금, 인력)을 적절하게 배치하여 원하는 테스트 결과를 생산적으로 도출하는 것을 의미합니다.
*   **Myers의 소프트웨어 테스팅 원칙**에 따르면, **결함을 많이 발견하는 테스트 케이스**가 좋은 테스트 케이스이며, 모든 결함을 발견하는 **완벽한 테스트는 불가능**합니다. 따라서 **리스크 기반 테스팅(Risk-based testing)**이 가장 효율적인 접근 방식입니다.
*   **리스크 관리 프로세스**
    *   **리스크**는 프로젝트의 목적(일정, 비용, 범위, 품질)에 부정적인 영향을 미칠 수 있는 잠재적인 문제입니다.
    *   **제품/품질 리스크**는 테스트 대상과 직접 관련이 있으며 제품의 품질에 영향을 미치는 리스크입니다.
    *   리스크 관리는 다음 세 단계로 진행됩니다:
        1.  **리스크 식별 (Risk Identification)**: 프로젝트나 제품의 리스크 요소를 찾아냅니다. 기능적/기술적 항목 분리, 요구사항 분석, 아키텍처 분석, 브레인스토밍 등이 활용됩니다.
        2.  **리스크 분석 (Risk Analysis)**: 식별된 리스크 항목별로 **장애 발생 가능성(likelihood)**과 **장애로 인한 영향력(impact)**을 평가하여 리스크의 우선순위를 결정합니다. 리스크 레벨은 심각성(Critical), 높음(High), 보통(Moderate), 낮음(Low), 없음(None) 등으로 분류할 수 있습니다.
        3.  **리스크 계획 (Risk Planning)**: 분석된 리스크 정보를 바탕으로 **대처 방안을 수립**하고, 리스크를 줄이기 위한 테스트 전략을 세웁니다.

**3. 소프트웨어 테스트 설계 기법**

소프트웨어 테스트 설계 기법은 크게 두 가지 범주로 나뉩니다:

*   **명세 기반 테스트 (블랙박스 테스트, Black-box Test)**
    *   **소스 코드의 내부 로직은 고려하지 않고**, 소프트웨어의 **입력과 출력, 기능 명세**에 초점을 맞춥니다.
    *   주로 **요구사항 명세서**나 설계서로부터 테스트 케이스를 추출합니다.
    *   **블랙박스 테스팅의 종류**:
        *   **구문 테스팅 (Syntax Testing)**: 입력값의 적합/부적합 조건을 기준으로 테스트 케이스를 작성합니다.
        *   **동치 클래스 분할 (Equivalence Class Partitioning)**: 입력값을 유사한 특성을 가진 그룹(동치 클래스)으로 나누고, 각 클래스에서 대표 값을 선택하여 테스트 케이스를 만듭니다. 유효/무효 동치 클래스를 모두 고려합니다.
        *   **경계값 분석 (Boundary Value Analysis)**: 입력값의 **경계(최소값, 최대값)**에서 오류가 자주 발생한다는 점을 이용하여, 경계값과 그 주변 값(경계값-1, 경계값+1)을 테스트 케이스로 활용합니다.
        *   **페어와이즈 (Pairwise)**: 여러 입력 변수들의 모든 조합을 테스트하는 것이 비효율적일 때, 각 입력 변수 쌍이 최소 한 번씩 조합되도록 테스트 케이스를 설계하여 효율성을 높이는 기법입니다.
        *   **에러 추정 (Error Guessing)**: 테스터의 경험, 지식 또는 과거 결함 데이터를 바탕으로 **잠재적인 오류를 예측**하고, 해당 오류를 발생시킬 수 있는 테스트 케이스를 직접 설계하는 기법입니다. HAZOP(Hazard and Operability) 가이드 워드를 활용하여 위험을 식별하는 데 도움을 받을 수 있습니다.

*   **구조 기반 테스트 (화이트박스 테스트, White-box Test)**
    *   **소스 코드의 내부 구조(로직)**에 초점을 맞추어, 코드의 모든 독립적인 경로를 실행함으로써 결함을 찾아냅니다.
    *   주로 프로그램 소스 코드로부터 테스트 케이스를 추출합니다.
    *   **ISO 26262**는 소프트웨어 단위 수준에서 **구조적 커버리지 메트릭**(Table 9)을 사용하여 테스트 범위를 정의할 것을 요구합니다.
    *   **화이트박스 테스팅의 종류 및 커버리지**:
        *   **경로 커버리지 (Basis Path Coverage)**: 프로그램의 제어 흐름을 **플로우 그래프(Flow Graph)**로 표현하고, **순환 복잡도(Cyclomatic Complexity)**를 계산하여 모든 독립적인 경로를 커버하는 테스트 케이스를 설계합니다. 순환 복잡도는 McCabe가 개발한 지표로, 코드의 논리적 복잡성을 정량적으로 측정합니다.
        *   **함수(Function) 커버리지**: 코드 내의 모든 함수를 한 번 이상 실행했는지 측정합니다.
        *   **구문(Statement) 커버리지**: 코드 내의 모든 실행 가능한 문장(statement)을 한 번 이상 실행했는지 측정합니다.
        *   **결정(Decision) 커버리지**: 코드 내의 모든 결정 지점(예: if, while 문의 조건)에서 가능한 모든 분기(참/거짓)를 한 번 이상 실행했는지 측정합니다.
        *   **조건(Condition) 커버리지**: 결정 지점 내의 개별 조건식들이 가능한 모든 결과(참/거짓)를 한 번 이상 가지도록 테스트했는지 측정합니다.
        *   **조건/결정 (Condition/Decision) 커버리지**: 모든 결정 지점과 모든 조건식의 결과가 모두 커버되도록 하는 기법입니다.
        *   **변형 조건/결정 (Modified Condition/Decision, MC/DC) 커버리지**: 항공, 자동차 등 안전 필수 시스템에서 요구되는 높은 수준의 커버리지로, 각 조건이 독립적으로 결정 결과에 영향을 미 미치는지 검증합니다.
        *   **다중 조건 (Multiple Condition) 커버리지**: 모든 조건 조합을 테스트하는 가장 포괄적인 커버리지 기법입니다.
