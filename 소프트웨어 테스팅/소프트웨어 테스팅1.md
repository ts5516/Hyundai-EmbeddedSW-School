### 1. 소프트웨어 테스팅의 이해 및 중요성 (슬라이드 1-7)

*   **교육 목표**는 V&V (Verification & Validation)에 대한 이해와 A-SPICE 기반의 소프트웨어 테스트 프로세스 요건(SWE.4, SWE.5, SWE.6, VAL.1), 그리고 ISO 26262 Part 6 기반의 주요 소프트웨어 테스트 기법을 이해하는 것입니다 [s].
*   역사적으로 **소프트웨어 결함으로 인한 주요 사고** 사례들이 언급됩니다 (Therac-25 방사선 치료기, Ariane 5호 인공위성, Toyota Lexus ES 350 자동차, Boeing 737 MAX 항공기 등) [s].
*   현대 자동차의 소프트웨어 규모는 **100만 라인 코드(MLOC)에 70-100개 ECU**를 포함하며, 우수 소프트웨어 기업들도 **1천 라인 코드당 8-12개의 결함**이 발생합니다 [s].
*   **"눈덩이 효과(Snowball Effect)"**: 개발 초기 단계에서 결함을 수정하는 비용이 가장 적으며, 출시 이후 현장에서 결함을 수정하는 비용은 **개발 초기보다 40-1000배** 이상 소요될 수 있습니다 [s]. 이 문제를 해결하기 위해 **"Shift Left"** (개발 초기에 테스트를 시작하여 결함을 조기에 발견하고 수정하는) 개념이 강조됩니다 [s].
*   **소프트웨어 안전 확보 컨셉**:
    *   **결함 전파(Fault Propagation)**: Mistake(실수)가 Fault(결함)로 이어지고, Fault는 Error(오류)를 유발하며, Error는 Failure(고장)를 발생시켜 Harm(피해)을 초래하고, 이는 Hazard(위험)로 발전하여 최종적으로 Accident(사고)로 이어질 수 있습니다 [s].
    *   **소프트웨어 안전 확보를 위한 4가지 방법**:
        *   **결함 예방(Fault Prevention)**: 사람이 실수하지 않도록 하는 방법 (예: 코딩 표준 준수, Strongly Typed Programming Language 사용) [s].
        *   **결함 검출(Fault Detection)**: 결함을 찾아내는 방법 (예: 정적/동적 테스팅, 코드 리뷰) [s].
        *   **결함 제거(Fault Removal)**: 검출된 결함을 없애는 방법 (예: 디버깅) [s].
        *   **결함 허용(Fault Tolerance)**: 런타임에 결함이 발생해도 오류를 유발하지 않거나 고장으로 이어지지 않도록 하는 방법 (예: Redundancy Design, Diversity Design) [s].

### 2. A-SPICE와 ISO 26262 (슬라이드 8-11)

*   **A-SPICE(Automotive SPICE)**는 조직 수준의 차량 개발 프로세스를 다루고, **ISO 26262**는 제품(시스템, SW) 수준의 기능 안전(Functional Safety)을 다룹니다 [s].
*   안전 최우선(Safety Critical) 시스템 개발에서 표준 준수의 필요성이 강조됩니다 [s].
*   **A-SPICE 4.0**은 프로세스 참조 모델(PRM)과 프로세스 평가 모델(PAM)로 구성되며, 이는 ISO/IEC 33020:2019 및 ISO/IEC 15504-5:2006의 관련 자료를 포함합니다.
*   **A-SPICE 4.0의 SWE.3 (Software Detailed Design and Unit Construction) 및 SWE.4 (Software Unit Verification)**의 Base Practice(BP) 정의가 3.1 버전과 비교하여 변경되었습니다 [s].
*   **ISO 26262**는 소프트웨어 단위 검증(Software Unit Verification)을 위한 다양한 방법을 제시합니다 [s].

### 3. 시스템 검증 vs 소프트웨어 검증 및 품질 정의 (슬라이드 12-18)

*   **시스템 검증**은 하드웨어적 요소 포함 및 하드웨어와 소프트웨어, 서브 시스템의 통합 환경(HIL 등)에서 수행됩니다 [s].
*   **소프트웨어 검증**은 소스코드 수준의 검증이며, 테스트 보드, 에뮬레이터, 가상 환경(SIL/PIL/HIL)을 활용합니다 [s].
*   **품질(Quality)**은 "제품 또는 서비스가 명시적, 묵시적 요구를 만족시키는 능력에 관한 특성"으로 정의됩니다 (ISO 9001:2015) [s].
*   **소프트웨어 품질**은 "소프트웨어가 필요한 속성을 보유하고 있는 정도(사용자의 기대 수준을 만족할 수 있는 정도)를 결정하는 소프트웨어의 특성" (IEEE)으로 정의됩니다 [s].
*   **품질 확보 방법 유형**에는 **프로세스 품질**(V&V, 품질 보증 QA)과 **제품 품질**이 있습니다 [s].
*   **ISO 25010 (과거 ISO 9126)의 소프트웨어 품질 특성**: 기능성, 신뢰성, 사용성, 효율성, 유지보수성, 이식성, 상호운영성, 보안성 [s].
*   **V&V (Verification & Validation)**:
    *   **검증(Verification)**: **"제품이 올바르게 생성되고 있는가?(Are we building the product right?)"** - 소프트웨어가 요구사항에 부합하게 구현되었음을 보장하는 활동 [s].
    *   **확인(Validation)**: **"올바른 제품을 생성하고 있는가?(Are we building the right product?)"** - 소프트웨어가 고객이 의도한 요구사항에 따라 구현되었음을 보장하는 활동 [s].

### 4. 소프트웨어 테스팅 프로세스 및 용어 (슬라이드 19-34)

*   **A-SPICE 4.0**에서는 추적성/일관성(Traceability/Consistency)이 강조되며, 이는 ML 관련 프로세스에서도 나타납니다 [s, 547, 548].
*   **소프트웨어 테스트**는 "정상 조건 및 비정상 조건 사이의 차이점을 발견하기 위해 소프트웨어 항목을 분석하고, 분석된 항목의 특성을 평가하는 프로세스" (IEEE-Std-829) 입니다 [s].
*   **주요 용어 정의**:
    *   **결함(Defect, Fault), 버그(Bug)**: 실패/고장 또는 문제의 원인이 되는 제품 내 결점 [s].
    *   **에러(Error)**: 결함의 원인으로 사람이 만든 실수 [s].
    *   **실패/고장(Failure), 문제(Problem)**: 제품의 결함이 있는 부분이 실행될 때 발생되는 현상 [s].
    *   **ISO 26262의 용어**: Mistake(실수) -> Fault(결함) -> Error(오류) -> Failure(고장)로 이어지는 결함 전파 개념을 설명합니다 [s].
*   **소프트웨어 테스트의 2가지 종류**:
    *   **정적(Static) 테스트**: 소프트웨어를 실행하지 않고 결함 발견 (예: 동료 검토, 정적 분석) [s].
    *   **동적(Dynamic) 테스트**: 소프트웨어를 실행하여 결함 발견 [s].
*   **V모델**: 소프트웨어 개발 생명주기의 각 단계와 그에 상응하는 테스트 단계를 나타냅니다. 일반적으로 **정적 테스트는 초기 단계**에서, **동적 테스트는 후기 단계**에서 수행됩니다 [s].
*   **소프트웨어 테스트 프로세스 (ISO/IEC/IEEE 29119 기준)**:
    *   **테스트 계획 및 제어(Test Planning and Control)**: 테스트 목적/목표 설정, 전략 개발(리스크 분석), 종료 조건, 추정, 조직 구성 [s].
    *   **테스트 분석 및 설계(Test Analysis and Design)**: 테스트 베이시스 검토, 테스트 용이성 평가, 테스트 상황/요구사항/데이터 식별, 논리적 테스트 케이스 설계 [s].
    *   **테스트 구현 및 실행(Test Implementation and Execution)**: 테스트 케이스 최종 구현, 프로시저 생성, 테스트 환경 구축 확인 [s].
    *   **종료 조건 평가 및 보고(Evaluating Exit Criteria and Reporting)**: 종료 조건 달성 여부 확인, 최종 테스트 보고서 작성 [s].
    *   **테스트 완료 활동(Test Closure Activities)**: 산출물 확인, 테스트웨어 보관, 테스트 프로세스 평가 [s].
*   **테스트 베이시스(Test Basis)**: 테스트 케이스 작성을 위한 근거 산출물 (예: 요구사항 명세서) [s].
*   **테스트 케이스(Test Case)**: 특정 요구사항 검증을 위해 테스트 조건, 입력값, 예상 출력값, 실제 수행 결과 등을 기록하는 것 [s].
*   **테스트 데이터(Test Data)**: 테스트 중 사용되는 데이터 (입력값, 예상 결과, 파일, 데이터베이스 등) [s].
*   **테스트 종료 조건(Test Exit Criteria)**: 수행된 작업의 완료 기준 [s].
*   **프로세스 정의 방법: ETVX (Entry Criteria, Task, Verification, eXit Criteria)**: 프로세스 단계별 수행 활동을 체계적으로 정의하는 방법 [s].

### 5. 테스트 커버리지 및 원리 (슬라이드 35-37)

*   **테스트 커버리지(Coverage)**: 테스트 케이스 수행 시 테스트 대상을 몇 %나 실행했는지 알려주는 지표 [s].
    *   **요구사항 커버리지**: 테스트 케이스가 요구사항을 얼마만큼 실행했는지 측정 (주로 블랙박스 테스트에 사용) [s].
    *   **소스코드 커버리지**: 테스트 케이스가 소스코드를 얼마만큼 실행했는지 측정 (주로 화이트박스 테스트에 사용) (예: 문장 커버리지, 결정 커버리지) [s].
*   **테스트 원리**:
    1.  **테스트는 결함이 존재함을 밝히는 활동** [s].
    2.  **완벽한 테스트는 불가능** (무수히 많은 조건, 입력값, 이벤트 조합) [s].
    3.  **테스트는 개발 초기에 시작** (Shift Left) [s].
    4.  **결함 집중**: 대부분의 결함은 소수의 모듈에 집중 [s].
    5.  **살충제 패러독스(Pesticide Paradox)**: 같은 테스트 케이스를 반복하면 더 이상 새로운 결함 발견 어려움 [s].
    6.  **테스트는 정황(Context)에 의존적** [s].
    7.  **오류 부재의 궤변(Absence of Errors Fallacy)**: 결함이 없음을 증명할 수 없으며, 모든 결함을 발견했더라도 올바른 제품이 아닐 수 있음 [s].

### 6. 소프트웨어 동적 테스팅 4단계 (슬라이드 38-54)

*   **동적 테스팅의 4단계**:
    1.  **단위 테스트(Unit Testing) (SWE.4)**: 소프트웨어의 개별 단위(함수, 모듈 등)가 올바르게 동작하는지 검증 [s].
        *   **테스트 드라이버(Test Driver)**: 상위 모듈을 대신하여 하위 모듈 테스트에 사용되는 임시 모듈 [s].
        *   **(테스트) 스텁(Stub)**: 하위 모듈을 대신하여 상위 모듈 테스트에 사용되는 임시 모듈 [s].
        *   **Test Harness**: 테스트 실행 및 제어를 위한 도구, 스크립트, HW, SW 등의 집합 [s].
        *   A-SPICE SWE.4에서는 "소프트웨어 단위 검증 측정 방법(Software Unit Verification measures)"을 명세하도록 합니다 [s].
    2.  **통합 테스트(Integration Testing) (SWE.5)**: 단위들이 결합되어 올바르게 상호작용하는지 검증 [s].
        *   **빅뱅(Big Bang) 통합**: 모든 모듈을 한꺼번에 통합하여 테스팅, 오류 발생 시 문제 지점 찾기 어려움 [s].
        *   **하향식(Top-Down) 통합**: 상위 모듈부터 점진적 통합 (하위 모듈에 스텁 필요) [s].
        *   **상향식(Bottom-Up) 통합**: 하위 모듈부터 점진적 통합 (상위 모듈에 드라이버 필요) [s].
        *   **지속적 통합(Continuous Integration, CI)**: 소스코드/소프트웨어 문제점을 조기에 발견하고 해결하기 위해 개발 시작부터 통합 빌드, 정적 분석, 테스트를 자동화하는 방법 [s]. "통합 지옥(Integration HELL)" 방지 [s].
        *   A-SPICE SWE.5에서는 "소프트웨어 통합 검증 측정 방법(Software integration verification measures)"을 명세하도록 합니다 [s].
    3.  **시스템 테스트(System Testing) (SWE.6)**: 통합된 시스템 전체가 요구사항을 충족하는지 검증 [s].
        *   A-SPICE SWE.6에서는 "소프트웨어 검증 측정 방법(Software verification measures)"을 명세하도록 합니다 [s].
    4.  **인수 테스트(Acceptance Testing) (VAL.1)**: 최종 사용자의 관점에서 제품이 의도한 사용 목적에 부합하는지 확인 [s].
        *   A-SPICE VAL.1에서는 "제품 확인 측정 방법(validation measures for product validation)"을 명세하고, 실제 운영 환경에서의 최종 사용자 기대 만족 여부를 확인합니다 [s].

### 7. 테스팅 전략 및 리스크 기반 테스팅 (슬라이드 55-63)

*   **동적 테스트의 목적**: "결함이 있음을 보여줄 뿐, 결함이 없음을 증명할 수는 없다" [s]. 효율적인 테스팅은 주어진 시간과 인력으로 오류를 발견할 확률이 높은 테스트 케이스를 찾아 실행하는 것입니다 [s].
*   **재테스팅(Re-Testing)**: 발견된 결함이 정상적으로 조치되었는지 확인하는 행위 [s].
*   **회귀 테스트(Regression Test)**: 변경된 부분으로 인해 변경되지 않은 부분에 의도치 않은 영향이 없는지 확인하는 테스트 [s]. A-SPICE 4.0의 여러 Base Practice에서 회귀 검증(Regression Verification)이 포함되어 있습니다 [s].
*   **효과적(Effective) 테스팅**: 계획하거나 원했던 테스트 결과를 도출하는 것 [s].
*   **효율적(Efficient) 테스팅**: 원했던 테스트 결과를 생산적으로 도출하고, 가용한 자원(시간, 자금, 인력)을 적절하게 배치하는 것 [s].
*   **리스크(Risk)**: 프로젝트 목적(일정, 비용, 범위, 품질 등)에 부정적인 영향을 끼칠 수 있는 잠재적인 문제 [s].
    *   **제품/품질 리스크**: 제품 품질에 직접 영향 (테스트 대상 관련) [s].
    *   **프로젝트/계획 리스크**: 프로젝트 성공에 직접 영향 (테스트/프로젝트 관리 관련) [s].
*   **리스크 기반 테스팅(Risk Based Testing, RBT)**: 테스트 자원이 부족할 때, 리스크를 정의/분석하고 우선순위에 따라 자원을 효율적으로 분배하여 테스트를 수행하는 전략 [s].
    *   **리스크 관리 프로세스**: **식별(Identification)** -> **분석(Analysis)** -> **계획(Planning)** -> **모니터링(Monitoring)** [s].
    *   **리스크 식별**: 프로젝트나 제품에 대한 리스크 요소 식별 (기능적/기술적 분리, 요구사항/아키텍처 기반 도출, 브레인스토밍) [s].
    *   **리스크 분석**: 리스크 아이템별 발생 가능성(likelihood)과 영향력(impact)을 평가하여 리스크 우선순위 결정 [s]. (예: 사용 빈도 × 결함 가능성) [s].
    *   **리스크 계획**: 식별된 리스크 레벨에 따라 완화 정책 수립 및 테스트 활동 강도 결정 (예: STTA(STrong Test Area)에서는 문장 커버리지 100%, 동료 검토 등) [s].

### 8. 동적 테스트: 테스트 설계 기법 (슬라이드 64-86)

*   **테스트 설계 기법 분류**:
    *   **명세 기반 테스트(Black-Box)**: 소스코드 로직 제외, 출력 값에 초점, 요구사항/설계서 기반 테스트 케이스 추출 [s].
    *   **구조 기반 테스트(White-Box)**: 소스코드 내 독립적인 경로 수행, 내부 구조 기반 테스트 케이스 추출 [s].
*   **블랙박스 테스팅 종류**:
    *   **구문 테스팅(Syntax Testing)**: 입력 변수의 적합/부적합 조건을 정의하고 테스트 (예: 사용자 이름 길이, 문자 타입) [s].
    *   **동치 클래스(Equivalence Class)**: 입력값을 유사한 동작을 보일 것으로 예상되는 그룹(동치 클래스)으로 나누어 각 클래스에서 하나의 대표값을 선택하여 테스트 [s].
    *   **경계값 분석(Boundary Value Analysis)**: 입력값의 경계값(최솟값, 최댓값, 경계 바로 안팎의 값)을 테스트 케이스로 작성하여 테스트 [s]. 경계에서 오류가 자주 발생하기 때문 [s].
    *   **페어와이즈(Pairwise)**: 여러 입력 변수가 있을 때, 각 입력값들이 다른 입력값과 최소한 한 번씩 조합을 이루도록 테스트 케이스를 생성 [s].
    *   **에러 추정(Error Guessing)**: 과거 경험, 직관, 시스템 지식 등을 바탕으로 잠재적인 오류나 취약점을 예측하여 테스트 케이스를 도출 [s]. (예: HAZOP 가이드워드 활용) [s].

### 9. 동적 테스트: ISO 26262의 테스트 요건 및 화이트박스 개요 (슬라이드 87-90)

*   **ISO 26262**는 소프트웨어 단위, 통합, 임베디드 소프트웨어 테스트를 위한 테스트 케이스 도출 방법론을 제시합니다 [s].
*   **화이트박스 테스팅 개요**: 프로그램 소스 코드의 내부 로직을 기반으로 모든 독립적인 경로를 수행하여 결함을 찾아내는 방법 [s].

### 10. 동적 테스트: 구조적 커버리지 (슬라이드 91-102)

*   **구조적 커버리지(Structural Coverage)**: 소스코드의 어느 정도를 테스트했는지 측정하는 지표.
    *   **경로 커버리지(Basis Path Coverage)**: 프로그램의 제어 구조를 Flow Graph로 표현하고, **순환 복잡도(Cyclomatic Complexity, CC)**를 계산하여 모든 독립적인 경로를 테스트합니다 [s].
        *   **Flow Graph**: 프로그램의 제어 흐름을 시각화 (Sequence, Selection, Iteration) [s].
        *   **순환 복잡도(CC)**: McCabe가 개발한 지표로, 프로그램의 논리적 복잡도를 정량적으로 측정. CC가 높을수록 복잡하고 결함 발생 가능성이 높습니다 [s]. (CC = Region 수, CC = Edge - Node + 2, CC = Predicate + 1) [s].
    *   **함수(Function) 커버리지**: 모든 함수가 한 번 이상 호출되었는지 측정 [s].
    *   **구문(Statement) 커버리지**: 모든 실행 가능한 문장이 한 번 이상 실행되었는지 측정 [s].
    *   **결정(Decision) 커버리지**: 모든 분기점(결정)의 가능한 모든 결과(참/거짓)가 한 번 이상 실행되었는지 측정 [s].
    *   **조건(Condition) 커버리지**: 결정문 내의 각 개별 조건(예: `A && B`에서 `A`와 `B` 각각)이 참/거짓 값을 한 번 이상 가졌는지 측정 [s].
    *   **조건/결정(Condition/Decision) 커버리지**: 조건 커버리지와 결정 커버리지를 모두 만족 [s]. 그러나 모든 조건 조합을 커버하지는 못함 [s].

### 11. 동적 테스트: 고급 구조적 커버리지 및 자동화 (슬라이드 103-109)

*   **변형 조건/결정(Modified Condition/Decision) 커버리지 (MC/DC)**: 각 조건이 결정의 결과에 독립적으로 영향을 미치는 것이 입증되었는지 확인 [s]. 안전 최우선 시스템에서 요구되는 높은 수준의 커버리지 (전수 테스트 대비 94% 효과성) [s].
*   **다중 조건(Multiple Condition) 커버리지**: 모든 조건의 가능한 모든 조합을 테스트 [s]. (테스트 케이스 수가 매우 많아짐) [s].
*   **테스트 자동화: `assert()`**: 테스트 코어에서 예상 결과와 실제 결과를 비교하는 데 사용되는 함수. `assert(boolean)`에서 boolean이 True이면 성공, False이면 실패 [s].
*   **Google Test (gtest)**: C++용 단위 테스트 라이브러리 [s]. `ASSERT_EQ`, `EXPECT_EQ` 등의 어설션 함수를 제공하며, 테스트가 독립적이고 반복 가능하도록 지원 [s].
*   **TDD(Test Driven Development)와 지속적 통합(CI)**: 문제의 크기가 작을 때 빠르게 해결하고 지속적으로 문제를 검증/해결한다는 동일한 목적을 가집니다 [s].
