### 소프트웨어 테스팅 : 결함 주입(Fault Injection) 테스트 ~ 소스코드 화이트박스 테스트 실습

이 섹션에서는 소프트웨어의 견고성과 안정성을 검증하기 위한 다양한 **동적(Dynamic) 테스트 기법**, 특히 **블랙박스 테스트**와 **화이트박스 테스트**에 중점을 두고 설명합니다.

**1. 결함 주입(Fault Injection) 테스트**
*   **정의**: 시스템에 의도적으로 결함을 주입하여 시스템이 비정상적인 상황에 어떻게 반응하고 복구하는지 확인하는 테스트 기법입니다. 이는 시스템의 **오류 허용성(Fault Tolerance)**을 평가하는 데 주로 사용됩니다.
*   **고려 사항**:
    *   **결함 유형**: 주입할 결함의 종류(예: CPU 오류, 메모리 오류, 통신 오류, 소프트웨어 버그 등)를 정의합니다.
    *   **주입 위치**: 결함을 주입할 시스템의 위치(예: 하드웨어, 소프트웨어, 네트워크 등)를 결정합니다.
    *   **주입 시점**: 결함을 주입할 특정 시간 또는 조건을 명시합니다.
    *   **관찰 및 측정**: 결함 주입 후 시스템의 동작을 관찰하고, 성능 저하, 오류 메시지, 복구 시간 등을 측정합니다.
*   **수행 절차**:
    1.  **결함 시나리오 정의**: 주입할 결함 유형, 위치, 시점 및 예상되는 시스템 동작을 정의합니다.
    2.  **테스트 환경 설정**: 결함 주입 도구 및 모니터링 시스템을 포함한 테스트 환경을 준비합니다.
    3.  **결함 주입**: 정의된 시나리오에 따라 시스템에 결함을 주입합니다.
    4.  **시스템 동작 관찰 및 데이터 수집**: 결함 주입 중 및 후에 시스템의 반응을 기록하고 데이터를 수집합니다.
    5.  **결과 분석 및 보고**: 수집된 데이터를 분석하여 시스템의 오류 허용성을 평가하고, 개선 사항을 도출합니다.

**2. 동적 테스트: ISO 26262의 테스트 관련 요건 (블랙박스 테스트)**
*   ISO 26262는 **테스트 케이스를 도출하는 방법**으로 여러 기법을 제시하며, **단위 테스트(Unit Verification)**, **통합 테스트(Integration Verification)**, **임베디드 소프트웨어 테스팅(Testing of Embedded)** 단계별로 적용 가능한 기법을 명시합니다.

**3. 블랙박스(Black Box) 테스팅 개요**
*   **정의**: **소스 코드의 내부 로직은 고려하지 않고**, 소프트웨어의 **입력과 출력**에만 초점을 맞춰 테스팅하는 방법입니다.
*   **테스트 케이스 도출**: 주로 **요구사항 명세서(SRS)나 설계서**를 기반으로 테스트 케이스를 추출합니다.
*   **예제**: 세 양수 A, B, C를 입력받아 가장 큰 수를 출력하는 프로그램에 대해, A, B, C가 가장 큰 경우나 음수/소수 입력 등 다양한 입력값에 대한 테스트 케이스를 작성할 수 있습니다.

**4. 블랙박스 테스팅 종류**

*   **구문 테스팅 (Syntax Testing)**:
    *   입력 변수의 적합/부적합 조건을 정의하고, 이에 따라 예상 출력값을 검증합니다. 예를 들어, 사용자 이름 입력 시 최소/최대 길이, 허용 문자 등의 규칙을 테스트합니다.
*   **동치 클래스 (Equivalence Class)**:
    *   유사한 방식으로 처리될 것이라고 예상되는 입력값 또는 출력값의 집합(동치 클래스)을 나누고, **각 클래스에서 하나의 대표값을 선택하여 테스트**합니다. 이를 통해 불필요한 중복 테스트를 줄이고 효율성을 높일 수 있습니다.
    *   **예제**: 회원가입 시 결제 금액에 따른 멤버십 등급(VVIP, VIP, Gold, Silver)을 구분하고, 각 등급 범위 내의 대표값을 선정하여 테스트합니다.
*   **경계값 분석 (Boundary Value Analysis)**:
    *   동치 클래스의 **경계에 있는 값**들이 오류를 유발할 가능성이 높으므로, 이 값들을 입력값으로 사용하여 테스트 케이스를 작성하는 기법입니다. 이는 동치 클래스 분석과 함께 사용될 때 효과적입니다.
*   **페어와이즈(Pairwise) 테스팅**:
    *   테스트에 필요한 각 입력값들이 다른 입력값과 최소 한 번씩 조합을 이루도록 테스트 케이스를 생성하는 방법입니다. 입력값의 모든 쌍의 개별 조합을 커버하여 테스트 케이스 수를 줄이면서도 효과적인 테스트를 가능하게 합니다. 수작업으로 추출하기는 어려워 **도구 사용이 권장**됩니다.
*   **에러 추정 (Error Guessing)**:
    *   **과거의 경험, 오류 데이터베이스, HAZOP(Hazard and Operability) 가이드 워드** 등을 기반으로 **잠재적으로 오류가 발생할 가능성이 높은 부분**을 추정하여 테스트 케이스를 작성하는 기법입니다. 이를 통해 명세 기반 테스트로는 발견하기 어려운 결함을 찾을 수 있습니다.
    *   **실습**: '스마트키 원격 시동' 기능이나 '속도 제한 보조 시스템' 시뮬레이터와 같은 시나리오에서, **초음파 센서나 광각 카메라의 오감지 사례**와 같은 과거 DB를 활용하여 오류를 추정하고 테스트 케이스를 보완하는 연습이 제시됩니다.

**5. 동적 테스트: ISO 26262의 테스트 관련 요건 (화이트박스 테스트)**
*   ISO 26262는 **소스 코드 커버리지 측정**을 통해 소프트웨어의 어느 정도를 테스트해야 하는지에 대한 요건을 제시합니다.

**6. 화이트박스(White Box) 테스팅 개요**
*   **정의**: **소스 코드의 내부 구조와 로직**을 기반으로 모든 독립적인 경로를 수행하여 잠재적인 오류를 찾아내는 방법입니다.
*   **테스트 케이스 도출**: 프로그램 소스 코드로부터 테스트 케이스를 추출합니다.

**7. 구조적 커버리지 종류 및 포함 관계**
*   화이트박스 테스팅에서 사용되는 주요 커버리지 지표에는 **구문(Statement) 커버리지, 결정(Decision) 커버리지, 조건(Condition) 커버리지, 조건/결정(Condition/Decision) 커버리지, 변형 조건/결정(Modified Condition/Decision) 커버리지(MC/DC), 다중 조건(Multiple Condition) 커버리지, 경로(Basis Path) 커버리지** 등이 있으며, 이들은 상위 커버리지가 하위 커버리지를 포함하는 계층적 관계를 가집니다.

**8. 화이트박스 테스팅 종류**

*   **경로 커버리지(Basis Path Coverage)**:
    *   **정의**: 프로그램 제어 구조를 **플로우 그래프(Flow Graph)**로 표현하고, **순환 복잡도(Cyclomatic Complexity)**를 계산하여 독립적인 경로의 수를 찾아 테스트 케이스로 선정하는 테스팅 기법입니다.
    *   **수행 프로세스**:
        1.  **Flow Graph 작성**: 프로그램의 내부 구조를 노드(Node)와 엣지(Edge)로 구성된 플로우 그래프로 표현합니다.
        2.  **순환 복잡도 계산**: McCabe의 순환 복잡도 공식을 사용하여 독립적인 경로의 수를 계산합니다. 공식은 `CC = R (영역의 수)`, `CC = E - N + 2 (엣지 - 노드 + 2)`, `CC = P + 1 (조건 노드 + 1)` 입니다.
        3.  **독립 경로 정의**: 계산된 순환 복잡도 횟수만큼 독립적인 경로들을 정의합니다.
        4.  **테스트 케이스 작성**: 정의된 각 경로를 테스트할 수 있는 입력값과 예상 출력값을 가진 테스트 케이스를 작성합니다.
    *   **예제**: 성적 관리 프로그램의 소스 코드를 플로우 그래프로 변환하고 순환 복잡도를 계산하여, 최소 3개의 독립 경로를 식별하고 각 경로에 대한 테스트 케이스를 제시합니다.
*   **함수(Function) 커버리지**:
    *   **정의**: 프로그램 내의 **모든 함수가 한 번 이상 호출**되는지를 측정하는 커버리지입니다.
    *   **실습**: `Add` 함수 등 특정 함수를 100% 함수 커버리지로 만족하는 테스트 케이스를 작성하는 연습이 제시됩니다.
*   **구문(Statement) 커버리지**:
    *   **정의**: 프로그램 내의 **모든 실행 가능한 구문이 한 번 이상 실행**되는지를 측정하는 커버리지입니다.
    *   **실습**: `Add` 함수 등 특정 함수의 구문 커버리지를 100% 만족하는 테스트 케이스를 작성하는 연습이 제시됩니다.
*   **결정(Decision) 커버리지**:
    *   **정의**: 프로그램 내의 **모든 결정(If, While, For 등 조건문)의 모든 분기(True/False)**가 한 번 이상 실행되는지를 측정하는 커버리지입니다.
    *   **실습**: `checkLow` 함수 등 특정 함수의 결정 커버리지를 100% 만족하는 테스트 케이스를 작성하는 연습이 제시됩니다.
*   **조건(Condition) 커버리지**:
    *   **정의**: 결정문 내의 **모든 개별 조건(예: A && B || C 에서 A, B, C 각각)의 모든 결과(True/False)**가 한 번 이상 실행되는지를 측정하는 커버리지입니다.
*   **조건/결정(Condition/Decision) 커버리지**:
    *   결정 커버리지와 조건 커버리지를 모두 만족하는 것을 의미합니다.
*   **변형 조건/결정 (Modified Condition/Decision) 커버리지 (MC/DC)**:
    *   **정의**: 모든 결정의 모든 조건이 최소 한 번씩 **독립적으로 전체 결정 결과에 영향을 미치는 경우**를 측정합니다. 이는 높은 안전 무결성 수준(ASIL)을 요구하는 자동차 소프트웨어 등에서 중요하게 요구되는 커버리지입니다.
    *   **효과**: 전수 테스트 대비 **94%**의 효과를 가질 수 있다고 합니다.
*   **다중 조건(Multiple Condition) 커버리지**:
    *   **정의**: 결정문 내의 **모든 개별 조건의 모든 가능한 조합**이 한 번 이상 실행되는지를 측정합니다. 이는 MC/DC보다 더 엄격한 커버리지입니다.
    *   **실습**: `if(a && b || c)`와 같은 조건에 대해 MC/DC 및 다중 조건 커버리지를 100% 만족하는 테스트 케이스를 도출하는 연습이 제시됩니다. C용 도구에서는 MC/DC를 자동 생성할 수 있다고 언급됩니다.

**9. ISO 26262에서 요구하는 커버리지 (단위 테스트)**
*   ISO 26262는 소프트웨어 단위 수준에서 **구조적 커버리지 측정**에 대한 요건을 정의합니다.

**10. 테스트 주도 개발 (Test Driven Development, TDD)**
*   **개념**: **테스트 코드를 먼저 작성**하고, 이 테스트를 통과할 수 있는 **최소한의 제품 코드만을 작성**한 후, 코드를 **리팩토링(Refactoring)**하는 과정을 반복하는 개발 방법론입니다.
*   **사용 예**: '더하기/빼기 함수'와 같이 간단한 기능에 대해 테스트 코드를 먼저 작성하고, 실제 함수를 구현하며 테스트를 통과시키는 방식으로 진행됩니다.
*   **장점**: 코드의 목적을 명확히 하고, 지속적인 코드 개선을 유도하며, 테스트 케이스가 문서의 역할을 수행합니다.
*   **단점**: 단위 테스트에만 몰입할 수 있다는 단점이 있습니다.
*   **테스트 프레임워크**: CppUTest, Unity, **Google Test** 등이 있으며, 프로젝트의 필요에 따라 가볍거나 무거운 프레임워크를 선택할 수 있습니다.
*   **assert() 사용**: 테스트 코드에서 **`assert(boolean)` 함수**를 사용하여 예상 결과와 실제 결과를 비교하고, 불일치 시 테스트 실패를 알립니다. Google Test는 `ASSERT_EQ`, `EXPECT_EQ`와 같은 다양한 검증 매크로를 제공합니다.
*   **Google Test 설명**:
    *   테스트는 독립적이고 반복 가능해야 하며, 잘 구조화되어 코드를 잘 반영해야 합니다.
    *   재사용 가능하고 플랫폼에 종속되지 않아야 합니다.
    *   테스트 실패 시 명확한 보고를 통해 버그를 쉽게 찾을 수 있도록 돕습니다.
    *   테스트 작성자의 편의를 높여 테스트 자체에 집중할 수 있게 합니다.
    *   빠른 테스트 실행을 지원하며, 공유 리소스 재사용 및 set-up/tear-down 메소드 활용이 가능합니다.
*   **TDD와 지속적 통합(CI)**:
    *   TDD와 CI는 **작은 크기의 문제를 조기에 발견하고 해결**하여 품질과 안정성을 지속적으로 확보한다는 동일한 목적을 가집니다. CI는 소프트웨어를 빠르게 통합하는 활동이며, TDD와 연계하여 개발 초기부터 품질을 검증하는 데 효과적입니다.

**11. [실습] 소스코드 화이트박스 테스트 실습**
*   **목표**: Cyber-dojo 웹사이트를 활용하여 `google Test` 프레임워크로 화이트박스 단위 테스트를 경험하는 실습입니다.
*   **과제**: 'Statement Coverage'를 100% 만족하는 테스트 케이스를 작성하고, 이를 Cyber-dojo에서 실행하여 실제 결과를 기록합니다.
