# 임베디드 리눅스 GPIO 프로그래밍 및 프로세스 이해

## 1. 임베디드 리눅스 GPIO 프로그래밍

### 1.1. Memory Mapped I/O (MMIO)

- **개념**: 주변장치(Peripheral)의 제어 레지스터를 메모리 공간의 특정 주소에 매핑하여, CPU가 메모리에 접근하는 것과 동일한 방식으로 하드웨어를 제어하는 기법.
- **라즈베리 파이 4 메모리 맵**:
  - 라즈베리 파이의 주변장치(GPIO, UART, SPI 등)는 물리 메모리 주소 공간에 특정 영역을 할당받아 매핑되어 있음.
  - 예를 들어, GPIO 관련 레지스터는 `0xFE200000` (`GPIO_BASE`) 부터 시작하는 주소에 위치.
- **`mmap()`을 이용한 GPIO 제어**:
  - **문제점**: 리눅스에서 사용자 모드(User Mode) 애플리케이션은 보안을 위해 커널 공간 및 물리 메모리 주소에 직접 접근할 수 없음.
  - **해결책 (`mmap`)**: `/dev/mem`이라는 특수 파일을 사용하여 물리 메모리 주소(GPIO 레지스터 주소)를 프로세스의 가상 메모리 공간에 매핑.
    - `open("/dev/mem", O_RDWR)`: 물리 메모리에 접근할 수 있는 파일 디스크립터를 얻음.
    - `mmap(NULL, size, PROT_RW, MAP_SHARED, fd, GPIO_BASE)`: GPIO 제어 레지스터의 물리 주소를 가상 주소 공간으로 매핑.
    - 매핑된 가상 주소를 포인터처럼 사용하여 GPIO 레지스터 값을 직접 읽고 쓸 수 있음.
- **실습**:
  - **LED 제어**: `mmap`으로 GPIO 제어 영역을 매핑한 후, GPIO 핀의 방향을 출력으로 설정하고(`GPFSELn`), `GPSETn`(ON) 및 `GPCLRn`(OFF) 레지스터에 값을 써서 LED를 점등/소등.
  - **Switch 입력**: 핀 방향을 입력으로 설정하고, `GPLEVn` 레지스터 값을 읽어 스위치 상태를 확인.

## 2. 임베디드 리눅스 커널과 프로세스

### 2.1. 임베디드 시스템 vs 범용 시스템

- **임베디드 시스템**: 특정 목적(차량 제어, 가전제품 등)을 위해 설계된 전용 컴퓨터 시스템. HW/SW가 목적에 맞게 최적화됨.
- **범용 시스템**: 다양한 목적(PC, 서버 등)으로 사용되며, 범용 운영체제(Windows, Linux 등)를 활용.

### 2.2. 프로그램과 프로세스

- **프로그램 (Program)**: 실행 가능한 파일 형태로 디스크나 Flash에 저장된 코드 덩어리.
- **프로세스 (Process)**: 프로그램이 메모리에 적재되어 실행 중인 상태. 독립된 메모리 공간(Code, Data, Stack, Heap)을 할당받음.

- **프로세스 메모리 구조**:
  - `.text`: 실행 코드 (명령어). Read-Only.
  - `.data`: 초기화된 전역/static 변수.
  - `.bss`: 초기화되지 않은 전역/static 변수 (실행 시 0으로 초기화).
  - `heap`: 동적 메모리 할당(`malloc`)을 위한 공간.
  - `stack`: 함수 호출 시 지역 변수, 매개변수, 복귀 주소 등을 저장. LIFO(Last-In-First-Out) 구조.

### 2.3. 프로세스 관리

- **계층 구조**: 모든 프로세스는 부모-자식 관계를 형성. `init` 또는 `systemd`(PID 1)가 모든 사용자 프로세스의 최상위 조상.
- **시스템 콜 (System Call)**:
  - `fork()`: 자신을 복제하여 **자식 프로세스**를 생성. 부모와 자식은 코드와 데이터를 공유하지만 독립적인 메모리 공간을 가짐.
  - `exec()`: 현재 프로세스의 메모리 공간을 새로운 프로그램으로 덮어쓰기(Overlay).
  - `wait()`: 부모 프로세스가 자식 프로세스가 종료될 때까지 대기.
  - `exit()`: 프로세스 종료. 종료 코드를 부모에게 전달.
- **좀비 프로세스 (Zombie Process)**: 자식 프로세스가 종료되었으나 부모가 `wait()`를 호출하지 않아 PCB(Process Control Block)가 정리되지 않은 상태.

### 2.4. 스레드 (Thread)

- **개념**: 프로세스 내에서 실행되는 "경량 프로세스". 하나의 프로세스는 여러 스레드를 가질 수 있음.
- **특징**:
  - **자원 공유**: 스레드는 프로세스의 `.text`, `.data`, `heap` 영역을 공유.
  - **독립된 실행 흐름**: 각 스레드는 자신만의 **스택**과 **레지스터** 값을 가짐.
  - **낮은 오버헤드**: 프로세스 생성/전환보다 스레드 생성/전환 비용이 훨씬 저렴.
- **스레드 동기화 문제 (Thread Safety)**:
  - **문제점**: 여러 스레드가 공유 자원(전역 변수 등)에 동시에 접근하면 데이터 무결성이 깨질 수 있음 (Race Condition).
  - **해결 방안**:
    - **Mutex (뮤텍스)**: 공유 자원에 접근하는 코드 영역(임계 구역)을 `lock`과 `unlock`으로 감싸 한 번에 하나의 스레드만 접근하도록 제한.
    - **TLS (Thread Local Storage)**: `__thread` 키워드를 사용하여 스레드마다 독립적인 전역 변수를 할당. 스레드 간 불필요한 데이터 공유를 줄여 동기화 오버헤드를 감소시킴.

### 2.5. 스케줄링

- **정의**: 여러 개의 실행 가능한 Task(프로세스/스레드) 중 어떤 것을 CPU에 할당할지 결정하는 과정.
- **컨텍스트 스위칭 (Context Switching)**: 현재 실행 중인 Task의 상태(레지스터 값 등)를 PCB에 저장하고, 새로 실행할 Task의 상태를 PCB에서 불러와 CPU에 적재하는 과정.
- **리눅스 CFS (Completely Fair Scheduler)**:
  - **개념**: 각 Task에 `vruntime`(가상 실행 시간)을 부여하고, `vruntime`이 가장 작은 Task에게 CPU를 할당하여 공정한 실행 기회를 보장.
  - **실시간 스케줄링**: `SCHED_FIFO` (선점형 선입선출), `SCHED_RR` (라운드 로빈) 같은 정책을 제공하여 우선순위가 높은 Task가 먼저 실행되도록 보장. 일반 CFS Task보다 우선권이 높음.
