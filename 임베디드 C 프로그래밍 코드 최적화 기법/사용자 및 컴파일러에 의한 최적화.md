### **1. 사용자에 의한 최적화 기법 (프로그래머가 직접 제어)**

컴파일러에만 의존하지 않고, 코드를 작성하는 단계에서 성능을 끌어올릴 수 있는 기법들입니다.

#### **가. 분기 최적화**
*   **공통 연산 추출**: `if-else if` 문 안에서 반복되는 연산(`a * b`)이 있다면, 조건문 밖으로 빼내어 한 번만 계산. 불필요한 중복 연산을 줄이는 가장 기본.
*   **이진 분리 분기 (Binary Split Branching)**: `if-else if`가 길게 이어질 경우, 선형적으로 하나씩 비교하지 말고 이진 트리 형태로 조건을 구성. 최악의 경우 비교 횟수를 N에서 log₂(N)으로 크게 줄여 성능 향상.
*   **`if` vs `switch`**
    *   **`if`가 유리할 때**: 조건이 복잡한 논리식, 범위 비교, 비연속적인 값일 때 사용.
    *   **`switch`가 유리할 때**: case가 많고, 연속적인 정수 값일 때 사용. 컴파일러가 이걸 보고 **점프 테이블(Jump Table)**을 생성하여 O(1) 시간 복잡도로 분기하므로 매우 빠름.

#### **나. 루프 최적화**
루프는 프로그램 성능 저하의 주범이므로 최적화 효과가 큽니다.
*   **루프 풀기 (Loop Unrolling)**: 반복 횟수가 적은 루프의 내용을 풀어써서 루프 제어(비교, 점프)에 드는 오버헤드를 줄임.
*   **루프 병합 (Loop Fusion)**: 비슷한 두 개의 인접 루프를 하나로 합쳐 오버헤드 감소.
*   **루프 불변식 이동 (Loop Hoisting)**: 루프 안에서 결과가 변하지 않는 연산이나 포인터 접근은 루프 시작 전에 미리 계산.
*   **루프 변수**: `register int`를 사용하고, `i < 100` 보다 `i--`를 써서 0과 비교하게 만들면 'zero flag'만 확인하므로 더 빠를 수 있음.

#### **다. 제어 흐름 및 연산 최적화**
*   **저비용 연산자 사용**: `나눗셈 > 곱셈 > 덧셈/뺄셈 > 비트 연산` 순으로 비용이 높음. `x * 8` 대신 `x << 3` 같은 비트 시프트 연산을 활용.
*   **Short-circuit 활용**: `&&`에서는 `false`가 될 확률이 높은 조건을, `||`에서는 `true`가 될 확률이 높은 조건을 앞에 배치하여 불필요한 뒷부분 조건 검사를 생략.
*   **실수 연산 최소화**: `float`, `double` 연산은 매우 느리므로, 가능하면 고정 소수점 등 정수 연산으로 대체.

### **2. 컴파일러에 의한 최적화 (TASKING 컴파일러 중심)**

컴파일러 옵션을 어떻게 설정하느냐에 따라 코드의 성능과 크기가 극적으로 달라지는 것을 실습으로 확인했습니다.

#### **가. 최적화 레벨(-O) 및 방향성(Trade-off)**
*   **최적화 레벨**:
    *   **-O0**: 최적화 없음. 디버깅 시에만 사용.
    *   **-O1**: 기본적인 최적화. 디버깅에 큰 영향을 주지 않음.
    *   **-O2 (Default)**: 속도와 크기 모두 고려한 표준 최적화.
    *   **-O3**: 속도 극대화를 위한 가장 공격적인 최적화.
*   **최적화 방향성 (Trade-off)**: 속도와 코드 크기 중 무엇을 더 우선할지 결정.
    *   **Level 0 (Speed)**: 실행 속도 최우선. 코드 크기는 커질 수 있음.
    *   **Level 4 (Size)**: 코드 크기(ROM/RAM) 최소화 최우선. 속도는 느려질 수 있음.
    *   **실습 결과**: `-O2`에 `Level 0(Speed)`를 적용했을 때 실행 시간이 23us로 가장 빨랐고, `Level 4(Size)`를 적용했을 때는 36us로 느려졌지만 Hex 크기는 더 작아짐. **목표 시스템의 제약 조건에 맞춰 이 둘을 조절하는 것이 핵심.**

#### **나. 세부 최적화 옵션 (Pragma와 플래그)**
컴파일러가 내부적으로 수행하는 고급 최적화 기법들로, 이런 원리를 알고 있으면 코드 작성에 도움이 됩니다.
*   **공통 부분식 제거 (CSE)**: `(a*b) + 10`, `(a*b) + 20`과 같은 코드에서 `a*b`를 한 번만 계산.
*   **수식 단순화**: `(a + 0 + b * 1) * 8` 같은 불필요한 수식을 정리하고, 곱셈을 비트 시프트 `<<3`으로 변경.
*   **함수 인라이닝 (Inlining)**: 작은 함수는 호출하는 대신 함수 코드를 그 자리에 복사해 넣어 호출 오버헤드를 제거.
*   **코드 압축 (Reverse Inlining)**: 여러 번 반복되는 코드 조각을 하나의 함수로 만들어 코드 크기를 줄임.
*   **첨자 강도 완화 (Subscript Strength Reduction)**: 루프 안에서 `arr[i]`의 주소 계산 시 매번 `base + i * sizeof(T)` (곱셈)을 하는 대신, 포인터를 이용해 `ptr += sizeof(T)` (덧셈)으로 변경.
*   **Peephole, Coalescer**: 어셈블리 수준에서 불필요한 `mov` 명령어나 비효율적인 명령어 시퀀스를 찾아내어 최적화.

### **총정리 및 느낀 점**

최적화는 단순히 "빠르게" 만드는 것이 아니라 **사용자(프로그래머)의 코드 레벨 최적화**와 **컴파일러의 설정 최적화** 두 가지 축을 모두 이해해야 한다는 것을 깨달았습니다. 특히 컴파일러가 제공하는 다양한 옵션들이 어떤 원리로 동작하는지, 그리고 그 결과가 실행 시간과 메모리 사용량에 어떤 영향을 미치는지 실습을 통해 직접 확인하니 더욱 명확하게 이해되었습니다.

앞으로 코드를 짤 때는 루프나 분기문을 더 신경 써서 작성하고, 빌드 시에는 프로젝트의 요구사항에 맞춰 최적화 레벨과 방향성을 신중하게 선택하고 **반드시 성능을 측정해보는 습관**을 들여야겠습니다.
